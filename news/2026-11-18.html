Claude Code v2.1.326：常に「block」を返すフックが本当に止めるように。opusplan の自動圧縮も Opus に

11月17日 7:11ごろ（日本時間）のリリースで、フックの "decision": "block" がより多くの場面で効くようになり、「毎回 block を出力するだけ」のフックが呼び出しを止め始める可能性があります。サンドボックス内のコマンドはホーム配下の一部の重要フォルダに書けなくなり（sandbox.filesystem.allowWrite で許可）、plan モードの自動圧縮は opusplan なら Opus で走るため、Pro プランでは使用量が増えやすくなります。

👉 やってみる：上げてから、block を出すフックと opusplan の設定を探す。
claude update && claude --version && rg -n '"decision"|opusplan|allowWrite' ~/.claude/settings.json .claude/settings*.json ~/.claude/hooks .claude/hooks 2>/dev/null
block を条件なしで出力しているフックがあれば、止めたいときだけ出すように直す。Pro で使用量を抑えたい日は /model で opusplan から Sonnet に切り替えておく。

過去の障害を「差分から読める条件」付きのチェックリストにして、該当する項目だけエージェントに確認させる

Claude Code チームは39項目の信頼性チェックリストを持ち、各項目に「差分から読める発動条件」「確認内容」「元になった障害や PR」を書いています。Claude は差分を読んで条件に合う項目（たいてい3〜10個）だけを確認するので、誰も過去の障害を覚えておかなくて済みます。

👉 やってみる：リポジトリに docs/reliability-checklist.md を作り、1項目をこの形で書く（例：AppSync のスキーマ変更）。
- 条件: schema.graphql の型・フィールドを削除/改名/必須化した差分 確認: 既存クライアント（Next.js の生成済み型・Storybook のモック）が壊れないか。必須化なら既存データに値があるか 由来: （過去の障害や PR のリンク）
PR 前にこう頼む。
git diff main...HEAD を読んで、docs/reliability-checklist.md のうち「条件」に当てはまる項目だけを挙げ、各項目の確認を実際に行って、結果（OK/NG と根拠）を一覧にして。当てはまらない項目は理由を一言で。

🧭 エージェント活用スキル

エージェントと同じ思い込みを持たないテストで検査する：fast-check のプロパティテストを Vitest に足す

同じ記事は、エージェントが落としやすいのは人が想定しない境界値で、プロパティテストは「コードを書いたエージェントと同じ偏り」を持たない入力で検査できると勧めています。往復変換・不変条件・冪等性・最適化前後の一致の4つが典型です。

👉 やってみる：Vitest のプロジェクトで入れて、エージェントにこう頼む。
npm i -D fast-check @fast-check/vitest
この変更で触った関数について、壊れてはいけない性質（encode→decode で元に戻る／残高が負にならない／2回実行しても結果が同じ／旧実装と新実装の出力が一致）を挙げて、@fast-check/vitest の test.prop でプロパティテストを書いて。見つかった反例は修正前に私に見せて。

🔒 セキュリティ

公開したソースマップから社内パッケージ名を拾われる：依存の取り違え攻撃を .npmrc とビルド設定で塞ぐ

11月17日に GitHub Advisory に載った npm の signup-lib@99.99.99 は、公開されていた JavaScript のソースマップから見つけた社内パッケージ名をスコープなしで登録し、高いバージョン番号で社内版より優先させるものでした。postinstall でインストールしたマシンのホスト名を外部に送ります。

👉 やってみる：Next.js のビルドでブラウザ向けソースマップを公開していないか、社内パッケージがスコープなしでないかを確認する。
rg -n 'productionBrowserSourceMaps|sourcemap' next.config.* ; find .next/static -name '*.map' | head; rg -n '"name": "[^@]' packages/*/package.json; cat .npmrc
社内パッケージは @社名/ のスコープに寄せ、.npmrc に @社名:registry=社内レジストリURL を書いて公開レジストリから解決されないようにする。エージェントに依存を足させるときも同じルールを守らせる。

🔒 セキュリティ

AWS の AccessDenied を当て推量で広げない：IAM Access Troubleshooter で「どのポリシーが拒否したか」を引く

11月17日、IAM に Access Troubleshooter（パブリックプレビュー）が入り、対応 API の AccessDenied に authorization ID が付くようになりました。この ID から、評価されたポリシーと条件キーの値、どの文が拒否したかを取得できます（記録は少なくとも24時間保持）。エージェントに権限エラーを直させると "Action": "*" などで広げがちなので、原因を先に特定させます。

👉 やってみる：拒否されたのと同じリージョンで実行する（iam:GetRequestAuthorizationDetails 権限が必要）。
aws iam-toolbox get-request-authorization-details --region ap-northeast-1 --authorization-id <エラーに出たID>
エージェントへの頼み方：
AccessDenied のエラー文に authorization ID があれば、上のコマンドで評価結果を取得して、拒否したポリシーと文（Sid）と条件キーを特定して。ポリシーを広げる修正は、必要な Action と Resource に絞った差分を私に見せてから。ワイルドカードは使わない。

👥 チームTips

Lambda durable functions：止まりかけた実行を一時停止して、あとで続きから再開する

durable functions の実行を一時停止し、最後のチェックポイントから同じ関数バージョンで再開できるようになりました（既定では停止中の時間はタイムアウトに数えません）。下流の障害やモデルのレート制限のときにリトライを使い切らずに済み、個人データを含む完了済み実行のデータも保持期間前に削除できます。

共有用

Lambda durable functions で実行の一時停止・再開・削除ができるようになりました。下流サービスの障害やモデル API のレート制限のときに、リトライを使い切る前に止めて、直してから続きを再開できます。コンソール・CLI・SDK から操作できます。https://aws.amazon.com/about-aws/whats-new/2026/11/lambda-durable-pause-delete/

👥 チームTips

Cognito のトークン交換で、MCP サーバーやエージェントに「狭い権限の別トークン」を渡す

Cognito が OAuth 2.0 トークン交換（RFC 8693）に対応しました。ユーザーのトークンをそのまま転送せず、特定の下流サービス向けに範囲を絞った、リフレッシュトークンなしのトークンに交換できます。actor トークンを付けると act クレームで「エージェントが代理で呼んだ」ことが下流から分かります（Essentials / Plus プラン）。

共有用

Amazon Cognito が OAuth 2.0 のトークン交換に対応しました。MCP サーバーやエージェントがユーザーの代わりにバックエンドを呼ぶとき、元のトークンを転送せずに、宛先と権限を絞ったトークンに交換できます。act クレームで代理呼び出しかどうかも判別できます。https://aws.amazon.com/about-aws/whats-new/2026/11/cognito-token-exchange/

👥 チームTips

新しいゲートはいきなり止めず、まず「観察モード」で何が止まるかを記録する

Claude Code チームは、/code-review や /verify を通していないコミットを止めるゲートを off・observe・enforce の3段階で入れています。observe では「止めたはずのもの」を記録だけして誤検知を見直し、enforce でも同じセッションで2回止めたら3回目は通して、エージェントが立ち往生しないようにしています。

共有用

Claude Code チームのやり方で参考になったのが、コミットを止めるゲートを off / observe / enforce の3段階で入れることです。まず observe で「止めたはずのもの」を記録して誤検知を確かめてから enforce にすると、エージェントもチームも詰まりにくいです。https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/
