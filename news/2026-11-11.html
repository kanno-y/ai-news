👉 やってみる：次の実装で plan mode（Shift+Tab で切り替え）にして、計画が出たらこう送る。

🧭 エージェント活用スキル

サブエージェントの「テスト通りました」を信じず、親が検証コマンドを再実行して、最初の赤で止める

約12万行の Next.js/TypeScript で開発する筆者は、各ステップを新しいコンテキストのサブエージェントに実装させ、親（オーケストレーター）はその自己申告を無視して「Done when」のコマンドを自分で実行し直します。赤なら失敗出力を1回だけ戻し、まだ赤なら止める。壊れた1手の上に5手積まれるのが一番の失敗だからです。

👉 やってみる：.claude/agents/ の実装用サブエージェントか、Orca に分割作業を頼むときの指示に次を足す。
各ステップが終わったら、サブエージェントの報告ではなく、あなた自身で次を実行して結果を見ること: pnpm tsc --noEmit && pnpm vitest run --changed && pnpm lint 緑ならコミットして次へ。赤なら失敗出力をそのままサブエージェントに1回だけ返す。それでも赤なら、そこで止めてブランチはそのままにし、どのステップがなぜ失敗したかを報告すること。テストを skip・弱める・消すことで通すのは禁止。
コマンドは各リポジトリの package.json の scripts に合わせて置き換える。

エージェントの設定ファイルは「実行されるコード」：workspace-tools MCP や見覚えのない SessionStart フックを探す

Socket によると、悪意ある Ruby gem strutil-core 1.0.1 はインストール時に認証情報を盗み、ホーム配下の mcp.json などに workspace-tools という MCP サーバーを、ほかの設定に SessionStart フックを書き込みました。盗んだ Git 認証で .claude/settings.json・.cursor/mcp.json・CLAUDE.md・AGENTS.md（「最初のコマンドの前にセットアップスクリプトを実行して」と指示）をリポジトリにコミットする機能もあります。

👉 やってみる：自分の Mac とリポジトリを、エージェントで開かずにターミナルから点検する。
rg -n --hidden "workspace-tools|SessionStart" ~/.claude ~/.cursor ~/.config 2>/dev/null; ls -la ~/.config/index.js ~/.local/share/runtimes/sync.py 2>/dev/null; git log --since=2.weeks --name-only --oneline -- .claude .cursor CLAUDE.md AGENTS.md .vscode/tasks.json
見覚えのない MCP エントリやフック、自分が書いていない AGENTS.md の変更があれば、トークンを失効させる前に Socket の記事の手順を読む（GitHub トークンが無効になるとホームを消す仕掛けがあるため）。

🔒 セキュリティ

--ignore-scripts では防げない npm 改ざん：require した瞬間に動くコードがある

Greenflagged の調査では、11月3〜4日に @adminide-stack などの npm パッケージ12バージョンに、エントリファイル末尾へ eval(atob(…)) を足した改ざん版が出ました。install スクリプトはなく require した時点で動き、第2段階は npm 自身の lib/cli.js や VS Code・Cursor の起動ファイルに常駐します（npm は全バージョンを削除済み）。

👉 やってみる：lockfile に該当がないかを見る。
rg -n "@adminide-stack|@cdmbase|@pubngo-stack|cdeops" --glob "**/{package-lock.json,pnpm-lock.yaml,yarn.lock}"
あわせて、Claude Code や Cursor に「依存を足して」と頼むときのルールに「新しい依存を追加する前に、パッケージ名・公開日・メンテナー・最新版の dist-tag をユーザーに見せて承認を取る」を1行足す。ignore-scripts は install スクリプト対策であって、読み込み時に動くコードは止められない点を前提にする。

テストが消えて緑になるのを防ぐ：承認前に「受入テストの差分」だけを別に見る

SyncStaff の記事は、実装とテストを同じエージェントが直せると、境界のテストを2件消すだけで誤った実装でも緑になる例を示しています。レビューのときは、コードとは別に受入テストやテストファイルの変更を確認します。

共有用

エージェントの PR を承認する前に、git diff main --stat -- "*.test.ts" でテストの変更だけを先に見ると安心です。テストが減っていたら、仕様が変わったのか、通すために弱めたのかを確認しましょう。https://www.syncstaff.ai/blog/spec-driven-development-with-claude-code

👥 チームTips

サブエージェントへの指示に「上で書いたとおり」は使わない

サブエージェントは親の会話を見ていません。DEV の記事では、各ステップの指示に目的・触るファイル・触らないファイル・必要な型・真似するファイル・検証コマンドを全部書き込み、「as described above」は禁止しています。

共有用

サブエージェントや別セッションに作業を渡すときは、「上で書いたとおり」ではなく、目的・触るファイル・触らないファイル・検証コマンドを指示に全部書くと、渡した先で迷わなくなります。https://dev.to/diegoprieri/spec-to-pr-with-claude-code-what-the-agents-decide-and-what-i-still-decide-3eal
